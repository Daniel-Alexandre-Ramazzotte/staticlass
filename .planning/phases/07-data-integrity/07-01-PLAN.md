<objective>
Investigate the root cause of duplicate alternatives appearing in the app, deduplicate existing data, and harden the schema + migration scripts so the problem cannot recur.

The user also wants to refactor the question ID system — specifically the `original_id` string field used as an import key, which has known duplicate values in the SQLite source (126 questions share an `original_id` with another question). This refactor is the structural fix that removes the underlying ambiguity.

Output: clean alternatives table, hardened schema, refactored ID system.

<investigation>
## Known Suspects (read before planning)

### 1. Missing UNIQUE constraint on alternatives(question_id, letter)
`app/backend/statl/models/questions.py` — `Alternative` model has no `UniqueConstraint`. Only the ORM `id` PK prevents nothing. A bare `INSERT` loop can add letter "A" twice for the same question with no error.

### 2. Multiple migration scripts with overlapping data
Three scripts exist: `migrate_questoes.py`, `migrate_apostila.py`, `migrate_bcb.py`. Each does its own SELECT-before-INSERT check for alternatives, but if they import overlapping question sets and the timing or transaction isolation produces a race, duplicates can land. Confirm whether all three scripts import from the same SQLite source or different ones.

### 3. original_id duplicates in the SQLite source
CLAUDE.md documents: "126 questões têm `original_id` duplicado na fonte." When `migrate_questoes.py` processes these, multiple SQLite question IDs map to the same PostgreSQL `id` via `sqlite_id_to_pg_id`. The alternatives loop then processes alternatives from both SQLite rows, pointing at the same pg question — the SELECT check should catch this, but if it doesn't (transaction visibility, concurrent runs), duplicates occur.

### 4. No UNIQUE index on questions.original_id in PostgreSQL
The `original_id` column is `String(50), nullable=True` with no DB-level uniqueness guarantee. The migration relies on application-layer SELECT logic; a DB constraint would catch violations at the insert layer.

### Investigation Queries (run against production/local DB before implementing fixes)
```sql
-- How many (question_id, letter) pairs have duplicates?
SELECT question_id, letter, COUNT(*) AS cnt
FROM alternatives
GROUP BY question_id, letter
HAVING COUNT(*) > 1
ORDER BY cnt DESC;

-- Total affected questions
SELECT COUNT(DISTINCT question_id) AS questions_with_dup_alts
FROM (
    SELECT question_id
    FROM alternatives
    GROUP BY question_id, letter
    HAVING COUNT(*) > 1
) sub;

-- Questions with more than 5 alternatives total
SELECT question_id, COUNT(*) AS total_alts
FROM alternatives
GROUP BY question_id
HAVING COUNT(*) > 5
ORDER BY total_alts DESC
LIMIT 20;

-- Duplicate original_id in questions table
SELECT original_id, COUNT(*) AS cnt
FROM questions
WHERE original_id IS NOT NULL
GROUP BY original_id
HAVING COUNT(*) > 1
ORDER BY cnt DESC;
```

<task type="auto">
  <name>Task 4: Refactor original_id — add UNIQUE index and resolve source duplicates</name>
  <read_first>
    - app/backend/statl/models/questions.py
    - app/backend/statl/migrate_questoes.py
  </read_first>
  <action>
    The `original_id` field is a String(50) with no DB-level uniqueness. 126 questions in the SQLite source share an `original_id` with another question, meaning the SELECT-before-INSERT import logic silently maps multiple SQLite rows to the same PostgreSQL row.

    **Decide on the refactor strategy** (investigate first, then pick):

    **Option A — Partial unique index (recommended if duplicates are all NULL or non-NULL)**
    ```sql
    CREATE UNIQUE INDEX uq_questions_original_id
    ON questions (original_id)
    WHERE original_id IS NOT NULL;
    ```
    If there are currently duplicate `original_id` values in the PostgreSQL table, they must be resolved first (keep lowest id, set others to NULL or a disambiguated value like `original_id || '_dup_' || id`).

    **Option B — Composite key: (original_id, source_db)**
    Add a `source_db` column ('apostila', 'bcb', 'professor') to questions. The UNIQUE constraint becomes `(original_id, source_db)`. This disambiguates duplicates that come from different source databases.

    **Option C — Drop original_id dependency, use content hash**
    Compute a SHA256 of `(issue, correct_answer)` as the idempotency key instead of relying on the upstream `original_id` which has known collisions. Store as `content_hash VARCHAR(64) UNIQUE`.

    **Recommendation:** Start with Option A (partial unique index) — it's the smallest diff and resolves the immediate problem. Option C is the cleanest long-term solution but requires touching more code.

    After choosing the strategy:
    1. Apply DDL to the live database
    2. Update `migrate_questoes.py` to use the new idempotency key
    3. Add a note in `migrate_questoes.py` documenting how duplicate `original_id` values in the SQLite source are handled (e.g., first-wins, second-wins, or merge)

    Run pytest after:
    ```bash

    ```
